## 3. تقوية نظام الإضافات

### 3.1 المعرف والمسارات

- أصبح `PluginIdValidator` المصدر المركزي لقبول المعرفات.
- يقبل معرف reverse-DNS صغير الحروف بطول أقصى 255، ويرفض الشرطات والمسافات و`..`
  والمسارات المطلقة ومحاولات path traversal.
- تُحوّل مسارات التخزين إلى canonical paths ويُشترط بقاؤها داخل مجلد الإضافات.
- تُرفض transaction directories والنسخ الاحتياطية غير النظامية أو الرمزية.
- تُرفض حزمتان مثبتتان تدّعيان Plugin ID نفسه.

### 3.2 التوافق والاعتمادات

- يُفحص مجال `min_ide_version..max_ide_version` قبل تحميل كود الإضافة.
- تُرفض النسخ غير الصالحة والمجالات المعكوسة والمضيفات الواقعة خارج المجال.
- Plugin API/ABI في العقد الحالي **مربوط بإصدار IDE**، وليس له بروتوكول runtime مستقل؛
  لذلك يوثق `PLUGIN_API_CHANGELOG.md` أول إصدار IDE لكل قدرة API، ويُفرض الحد الأدنى
  والأقصى قبل إنشاء class loader. بهذا حُفظ عقد الإضافات الحالي بدل اختراع رقم إصدار
  موازٍ لا يمثل ABI الحقيقي.
- تُرتب الاعتمادات dependency-first بصورة حتمية، وتُرفض التبعيات المفقودة والدورات.

### 3.3 التوقيع والثقة وDeveloper Mode

في الوضع العادي:

- تُرفض الحزمة غير الموقعة.
- الإضافة الجديدة يجب أن يطابق signer set الخاص بها signer set لناشر تطبيق IDE.
- تحديث إضافة موجودة يجب أن يحافظ على signer set نفسه تمامًا.
- المقارنة تتم على SHA-256 لشهادات كل الموقعين، لا على وجود توقيع شكلي فقط.

أضيف **Plugin Developer Mode** منفصل، معطل افتراضيًا داخل Developer Options، للسماح
بحزم التطوير المحلية أو غير الموقعة. هذا الوضع لا يعطل التحقق من ID أو المسار أو توافق
IDE/API أو الصلاحيات أو الاعتمادات.

### 3.4 التثبيت والتحديث الذري

- تُنسخ الحزمة الجديدة إلى staging وتُزامن إلى القرص ثم تُفحص بالكامل قبل النشر.
- تبقى النسخة القديمة موجودة كنسخة احتياطية حتى نجاح تحميل البديل.
- يستخدم الاستبدال `ATOMIC_MOVE` عندما يدعمه نظام الملفات، مع fallback مضبوط.
- عند فشل النسخ أو الفحص أو التحميل تُستعاد النسخة السابقة وتُعاد تهيئتها.
- transaction marker نفسه يُكتب ذريًا، وتوجد حالات `PREPARED` و`ACTIVATING`
  و`ROLLING_BACK` و`COMMITTED`.
- عند بدء المدير تُستعاد المعاملات المنقطعة والنسخ الاحتياطية اليتيمة بصورة محافظة.

غطت اختبارات `plugin-manager` المعرفات والمسارات، والثقة وDeveloper Mode، والتوافق،
والاعتمادات، والتثبيت/الاستبدال/rollback والتعافي بعد الانقطاع، وإدارة الموارد.

## 4. حماية خادم localhost

لم يعد مجرد الاتصال بـloopback يمنح الوصول إلى endpoints الديناميكية:

- يفرض `ServerConfig` الربط بـ`localhost` أو عنوان loopback صريح فقط.
- تُنشأ جلسة process-local عشوائية بقوة 256 bit.
- تتطلب كل مسارات `/pr/` capability واحدة صحيحة تمامًا عبر header داخلي أو cookie.
- المقارنة ثابتة الزمن، وتُرفض header/cookie المكررة أو الملتبسة.
- cookie مقيد بـ`Path=/pr/` ويحمل `HttpOnly` و`SameSite=Strict`.
- endpoints الحساسة `/pr/db` و`/pr/pr` لا تُفعّل إلا عندما تكون `BuildConfig.DEBUG` صحيحة؛
  وفي Release تعيد 404 حتى مع جلسة صحيحة.
- الطلب غير المصرح يعيد 404 من دون كشف مسار ملف أو سبب داخلي.
- فُرضت مطابقة Host وOrigin ورفض `Sec-Fetch-Site: cross-site`.
- رُفضت المسارات المطلقة الملتبسة و`.` و`..` وترميز slash/backslash.
- حُدد حجم request line والـheaders وعددها، وأضيف deadline للعميل البطيء.
- تُحجب قيم session header وcookie من السجلات، وتُعمم أخطاء SQLite ومسارات الملفات.

تغطي اختبارات JVM الجلسة والـHost/Origin والمسارات والحدود والمهلات والـendpoints. وأضيف
instrumentation test يعمل من test APK ذي package وUID مختلفين ويثبت أن طلب `/pr/pr`
من دون الجلسة يعيد 404 ولا يكشف مسارًا خاصًا.

## 5. سلسلة توريد الأصول

أصبح `config/assets-manifest.json` مصدر الحقيقة الوحيد للأصول الخارجية التي يستهلكها
البناء:

- schema: `1`
- manifest version: `2026.09.22.1`
- العدد: **20 أصلًا** — 9 debug و9 release و2 build-tooling.
- لكل أصل: ID، variant، المسار المحلي والبعيد، URL، الإصدار، ABI، الحجم، SHA-256،
  المصدر/revision، ومرجع الترخيص.
- 3 روابط GitHub versioned مصنفة `immutable-release`.
- 17 رابطًا موروثًا من `appdevforall.org` مصنفة صراحة `mutable-legacy`، لكنها fail-closed
  عند اختلاف الحجم أو SHA-256.

ربط `app/build.gradle.kts` أصول debug وrelease بالـmanifest فعليًا، وربطت أصول JDI
وKotlin Analysis API بالأداة نفسها. أزيلت من مسار الاستهلاك:

- MD5 والـsidecars المتغيرة.
- استعلام `latest` لوثائق offline؛ ثبت الإصدار `db-2025-07-16b`.
- مسارات SCP وGoogle Drive overwrite بوصفها مصدر حقيقة للبناء.

المنزل الموحد الآن:

- يقبل HTTPS فقط.
- يقفل الأصل لمنع التنزيل المتزامن المتعارض.
- يكتب إلى `.part` ويستأنف عبر `Range` بعد التحقق من `Content-Range`.
- يفرض الحجم المتوقع ويتحقق من SHA-256.
- لا يستبدل الوجهة السابقة إلا بعد نجاح التحقق و`ATOMIC_MOVE`.
- يحفظ partial المبتور للاستكمال، لكنه يحذفه عند checksum mismatch.

## 7. الحدود والمشاكل المتبقية

1. **17 أصلًا ما زالت على URLs موروثة قابلة للاستبدال.** الحجم وSHA-256 يمنعان قبول
   bytes مختلفة، لكن بقاء الرابط غير versioned يظل خطر availability/provenance. الحل الصحيح
   هو نشر objects versioned والاحتفاظ بها، لا تحديث digest لقبول تغيير صامت.
2. **اختبار العميل الخارجي جرى تجميعه ولم يُشغّل على emulator/device في هذا التشغيل.**
   منطق الحماية واختبارات socket/JVM نجحت، لكن إثبات اختلاف UID على جهاز حقيقي يبقى بندًا
   لتحقق device لاحق خالٍ من الأسرار.
3. **لم يُنتج Universal APK توزيعيًا في LAB.** تم تجميع مسار Kotlin والتكامل المستهدف،
   بينما بقي build التوزيعي خلف حارس workflow حتى مراجعة بنية التوقيع والنشر.
4. **الإضافات ما زالت تعمل داخل عملية التطبيق.** التوقيع والصلاحيات يحدان سطح الثقة، لكنهما
   ليسا sandbox للـbytecode؛ عزل العملية/IPC تحسين معماري لاحق وليس تغييرًا مناسبًا لهذه المرحلة.
5. تعذر البناء المحلي في بيئة العمل لغياب JDK/Android SDK؛ لذلك استُخدم runner مستضاف مع
   JDK 17 وAndroid SDK 36 ونجح. هذه ملاحظة بيئية وليست فشلًا في المصدر.

نُفذت المجموعات في commits مستقلة: تنظيف، تقوية الإضافات، حماية localhost، جرد الأصول،

   لترحيل الروابط الـ17 إلى أصول versioned ثم توقيع manifest/إضافة provenance آلي.
